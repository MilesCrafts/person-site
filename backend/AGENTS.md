# LEKANG JOURNAL 后端协作规则

## 1. 适用范围与规则继承

- 本文件适用于 `D:\lekang\backend` 及其全部子目录。
- 根目录 `D:\lekang\AGENTS.md` 继续有效；本文件只补充后端专用规则。
- 用户当前的明确指令优先于本文件；规则冲突或范围不清时，先报告并确认，不得擅自扩大任务。
- 后端线程只负责 `backend/`，不得擅自修改 `frontend/`、`deploy/` 或线上服务器。
- 跨模块修改前必须报告涉及文件、接口影响、验证范围和文档更新范围，并获得授权及对应所有者协调。
- 重要架构决策、接口契约、数据库策略和验证事实必须同步到 `docs/` 中对应文档，不能只存在于聊天记录。

## 2. 技术方案来源

- 后端实施基线是 `D:\lekang\docs\backend-technical-design.md`。
- 修改架构、数据库、公开 API、鉴权、媒体存储、搜索或部署前，必须先完整阅读该技术方案及相关文档。
- 本文件保存长期执行约束；技术文档保存完整设计、选型理由、ER 图、接口目录和 Roadmap，不在本文件中重复这些内容。
- 实现需求与技术文档冲突时不得静默选择；必须报告冲突、影响和可选方案。
- 用户确认架构变化后，再同步更新相关技术文档和接口契约。
- 不得因文档可能过期而自行猜测生产配置；应通过只读检查或用户确认获得事实。

## 3. 固定技术决策

- 使用 Java 21、Spring Boot 3.5、Spring MVC 和 Maven Wrapper。
- 使用 PostgreSQL、Spring Data JPA 和 Flyway；数据库结构只能通过 Flyway 演进。
- 使用 Spring Security 处理管理接口认证与授权，使用 Jakarta Validation 校验输入。
- 采用模块化单体，不拆分微服务。
- 所有业务 API 使用 `/api/v1`；公开读取接口与 `/api/v1/admin` 管理接口分离。
- 文章公开标识使用稳定 slug，已经公开使用的 slug 不得随意修改或复用。
- 正文以 Markdown 为原始格式，发布时生成并使用白名单清洗 HTML。
- 图片存储为文件或 S3 兼容对象；数据库只保存引用、URL 和必要元数据，不保存图片二进制。
- 搜索第一阶段优先使用 PostgreSQL。
- 单实例缓存优先使用 Caffeine。
- 不得擅自引入 Redis、Kafka、Elasticsearch、Kubernetes 或其他分布式复杂度。

## 4. 工程结构

后端按业务模块组织，推荐根包结构：

```text
com.lekang.journal
├── common
├── article
├── taxonomy
├── album
├── media
├── profile
├── homepage
├── search
└── admin
```

每个业务模块可按实际需要包含：

- `api`：Controller、请求 DTO、响应 DTO。
- `application`：用例、事务、权限和业务编排。
- `domain`：领域对象、枚举和业务规则。
- `infrastructure`：JPA Entity、Repository 和外部服务实现。

工程约束：

- 不使用全项目统一的 `controller`、`service`、`repository` 大目录堆放所有类。
- Controller 保持轻量，只负责协议适配、参数校验和调用用例，不直接访问 Repository。
- 业务规则不得写在 Controller 中；Repository 只负责数据访问。
- 不为了形式创建没有业务意义的抽象层或空目录。
- `common` 只能承载真正跨模块且稳定的能力，不能成为随意堆放工具类的垃圾目录。
- 模块之间通过清晰的 application/api 边界协作，避免循环依赖。

## 5. Java 编码规范

- 使用构造器注入，禁止字段注入。
- 优先使用不可变 DTO 和 Java `record`。
- API 请求和响应必须使用独立 DTO，禁止直接将 JPA Entity 用作请求对象或返回给客户端。
- 避免无意义的 Lombok 依赖；若项目已使用 Lombok，遵守项目现有约定。
- 方法保持单一职责，命名表达业务含义，不使用含糊缩写。
- 禁止捕获 `Exception` 后忽略或不处理。
- 不使用 `System.out` 输出日志；使用 SLF4J 参数化日志。
- 不记录密码、Cookie、Session、Token、密钥或正文隐私内容。
- 未知异常应在服务端记录堆栈，但不得将堆栈、SQL 或内部配置返回给客户端。
- 时间使用语义明确的 `Instant`、`OffsetDateTime` 或 `LocalDate` 等类型；业务时间按 UTC 持久化。

## 6. 事务规则

- 写操作在 application/service 层使用 `@Transactional`。
- 查询操作使用 `@Transactional(readOnly = true)`。
- Controller 不负责事务边界。
- 不在数据库事务中执行不必要的慢速外部网络调用。
- 缓存清理和非关键异步任务应在事务成功提交后执行。
- 发布文章等多步骤状态变化必须保持原子性。
- 切换首页 Feature 时必须在同一事务内确保旧 Feature 失效，并从数据模型上保证同一时间只有一个有效 Feature。
- 不滥用 `REQUIRES_NEW`。
- 异步方法不能假设继承调用线程的事务或安全上下文。

## 7. JPA 和 Repository 规则

- 关联默认使用 LAZY，禁止为方便而全局改成 EAGER。
- 列表查询只读取展示所需字段，不加载完整正文。
- 警惕并测试 N+1；需要时使用 DTO Projection、EntityGraph 或明确的 fetch join。
- Repository 方法只表达数据查询，不承载业务规则。
- 所有分页使用稳定排序，例如时间字段后追加主键排序。
- 不对大型结果集执行无分页查询。
- 对需要防止并发覆盖的编辑数据使用 `@Version` 乐观锁。
- Entity 的 `equals` 和 `hashCode` 不得依赖可变关联。
- 删除关联数据前必须检查引用关系和外键删除策略。

## 8. API 规范

- API 前缀固定为 `/api/v1`，资源路径使用复数名词。
- GET 只读取数据，不产生业务副作用。
- POST 用于创建资源或执行明确业务动作；PUT 用于完整更新；PATCH 仅在项目明确采用后使用。
- 发布、撤回等状态变化使用语义明确的动作端点。
- 所有列表接口必须分页；`page` 从 0 开始，`size` 必须限制合理最大值，当前上限为 50。
- 分页、导航和排序必须稳定；客户端排序字段只能取后端白名单。
- API 响应字段保持稳定，不得随意修改公开 slug、已有 URL 或字段语义。
- 成功响应直接返回资源或分页对象，不套无意义的 `code: 200` 包装。
- 错误响应使用 RFC 7807 Problem Details。
- 参数校验错误、资源不存在、状态冲突、未认证和无权限必须使用恰当且不同的状态码。
- 使用统一 `@ControllerAdvice` 处理异常，不向客户端暴露堆栈或数据库细节。
- OpenAPI 是前后端接口契约；API 变更必须同步更新 OpenAPI 和相关文档。

## 9. 数据库和 Flyway 规则

- 所有表结构、约束、索引及固定字典种子数据的变化必须通过有序 Flyway 迁移完成。
- 禁止在生产环境使用 `ddl-auto=update`、`create` 或 `create-drop`；生产环境使用 `ddl-auto=validate` 或等价的只校验策略。
- 禁止手工修改生产表结构代替迁移。
- 数据库表、字段、索引和约束使用 `snake_case`。
- 主键、唯一约束、外键、检查约束和必要索引必须明确声明，所有外键必须明确删除策略。
- slug 等公开标识必须有唯一约束；公开使用过的 slug 不得复用。
- Topic 必须属于对应 Category，该规则同时由应用校验和数据库组合外键或约束保证。
- 索引必须根据真实查询模式设计，并检查分页稳定性和查询计划。
- 迁移脚本进入共享环境后不得修改，应新增迁移版本。
- Flyway 必须能从空 PostgreSQL 数据库完整迁移。
- 生产迁移遵循向前兼容的 expand/contract 策略；迁移前必须备份数据库并确认恢复方式、旧应用兼容性和回滚路径。
- 不在数据库中保存图片二进制，不在迁移脚本中写入敏感配置。

## 10. 内容领域规则

- Article 状态至少包含 `DRAFT`、`PUBLISHED`、`ARCHIVED`。
- 公开接口只返回 `PUBLISHED` 且 `published_at` 不晚于当前时间的内容。
- slug 发布后保持稳定，标题变化不得破坏公开 URL。
- Topic 必须属于文章选择的 Category。
- 正文 Markdown 在发布时转换为安全 HTML，HTML 必须经过白名单清洗。
- 阅读时间由后端计算，并可支持人工修正。
- 删除文章优先归档或软删除。
- 媒体只有在未被文章或影集引用时才能物理删除。
- 同一时间只允许一个有效首页 Feature。
- 影集照片必须保留排序、Topic、日期、地点和图注能力。

## 11. 安全规则

- 禁止提交或写入文档的秘密包括数据库密码、Token、Cookie、Session、Access Key、Secret Key、私钥和生产证书。
- 密钥只能通过环境变量、服务器 Secret 或受控只读配置管理。
- 管理后台、内容编辑和上传必须在 HTTPS 下启用；站点仍为 HTTP 时只允许上线无需身份认证的公开读取接口。
- 密码使用 Argon2id 或 BCrypt 哈希，禁止保存或记录明文。
- 管理登录使用服务端 Session；Cookie 设置 `HttpOnly`、`Secure`、合适的 `SameSite`、路径和有效期。
- 管理写接口启用 CSRF 防护，管理接口统一要求管理员权限。
- 登录接口必须限流并记录失败事件，限流存储必须有容量上限和过期策略。
- 上传文件必须校验 MIME、扩展名、大小和图片尺寸，防止路径穿越与危险内容；公开前重新编码图片并移除敏感 EXIF。
- 不直接读取或信任客户端传来的 `X-Forwarded-For`；只信任受控代理链处理后的客户端地址。
- 后端端口和 PostgreSQL 端口不得开放公网。
- 管理接口和草稿响应使用 `Cache-Control: no-store`。
- Actuator 详细端点、Swagger UI 和生产 OpenAPI 不得直接暴露公网。

## 12. 缓存和异步规则

- 第一阶段只在收益明确的场景使用 Caffeine。
- 文章、首页、分类及相关缓存必须在对应写事务提交后正确清理。
- 不能用缓存掩盖错误查询、N+1 或缺失索引。
- 多实例或明确共享缓存需求出现前不引入 Redis。
- 异步任务必须幂等、可重试、可观测，并具有明确失败处理。
- 关键业务成功不能依赖无法确认结果的异步任务。
- 不为当前规模引入消息队列；关键媒体处理不得依赖进程重启后可能丢失的裸 `@Async`。

## 13. 日志与可观测性

- 使用 SLF4J 输出日志。
- 每个请求生成或传递 `requestId`。
- 请求日志记录 method、path、status 和 durationMs。
- 不记录密码、Cookie、Session、Token、密钥或正文隐私内容。
- 健康检查使用 Spring Boot Actuator，只公开必要的 health/readiness 信息。
- 监控 5xx、P95 延迟、数据库连接池、存储错误和登录失败。
- 错误日志必须包含足够的业务与请求上下文，但不能暴露密钥或隐私数据。
- 管理端关键操作需要业务审计，普通应用日志不能替代审计记录。

## 14. 测试要求

- 使用 JUnit 5。
- Controller 测试使用 MockMvc。
- 数据库集成测试使用 Testcontainers PostgreSQL，不使用 H2 代替关键 PostgreSQL 行为测试。
- 测试 Topic 与 Category 归属、文章状态转换和发布规则。
- 测试分页、稳定排序、搜索、归档以及上一篇/下一篇导航。
- 测试 Flyway 空库迁移、唯一约束、组合外键、检查约束和删除策略。
- 测试公开接口不会返回草稿或尚未到发布时间的内容。
- 测试管理接口认证、授权、Session 和 CSRF。
- 测试媒体任务幂等、失败重试和引用保护。
- 修复 Bug 时优先增加回归测试，不得删除或弱化测试只为让构建通过。

## 15. 构建与验证

- 执行命令前必须先读取实际存在的 `pom.xml` 和 Maven Wrapper，以项目真实配置为准，不得编造命令。
- 通常至少执行：

```text
# Windows
mvnw.cmd test
mvnw.cmd verify

# Linux/macOS
./mvnw test
./mvnw verify
```

- 数据库相关修改还必须验证：
  - Flyway 可以从空 PostgreSQL 数据库完整迁移。
  - 迁移可以在具有代表性的已有数据环境执行。
  - Repository 查询在 PostgreSQL 下通过。
  - 无明显 N+1 查询，并对重要查询检查索引和执行计划。
  - OpenAPI 与实现一致。
- 若本地缺少 Docker、PostgreSQL、Java 或必要环境，必须明确列出未执行的验证、原因和风险，不能声称全部通过。

## 16. 部署边界

- 后端生产监听地址固定为 `127.0.0.1:8081`。
- 公网只通过 Nginx 的 `/api` 反向代理访问后端。
- 不将 JAR、配置或日志放入前端网站根目录。
- 后端线程不得修改线上 Nginx、安全组、防火墙、端口或服务器配置，除非用户对具体操作明确授权。
- 生产配置使用 `prod` Profile，生产环境同域访问时不启用宽泛 CORS。
- 部署前必须执行适用的测试和构建、数据库备份、迁移兼容性检查与健康检查。
- 新 JAR 使用版本号，不直接覆盖唯一的上一版本，并保留明确可回滚版本。
- 未经用户明确要求，不执行部署、重启、生产数据库迁移或线上健康检查。

## 17. 修改边界

禁止以下行为：

- 未经授权修改 `frontend/`、`deploy/` 或其状态文档。
- 未经授权操作生产数据库、线上服务器、Nginx、域名、DNS、SSL、进程或防火墙。
- 使用 `git reset --hard`、强制推送或其他可能丢失修改的 Git 命令。
- 覆盖、删除或移动用户未提交修改、内容、图片和数据。
- 为实现局部功能重构整个后端、调整项目目录或扩大任务范围。
- 擅自更改技术栈、公开 API、slug、公开 URL 或稳定字段语义。
- 擅自引入微服务、Redis、Kafka、Elasticsearch、Kubernetes 或其他复杂中间件。
- 未执行适当测试就宣称任务完成，或把未运行、失败的验证描述为通过。
- 将临时进度、短期计划或每日状态写入本文件。
- 未经用户明确要求提交、推送、合并、变基或部署。

## 18. 完成任务后的报告

每次后端任务完成后必须报告：

- 完成内容。
- 修改文件。
- 数据库迁移。
- 新增或修改的 API。
- 实际执行的测试及结果。
- 未执行的验证及原因。
- 已知风险。
- 是否影响前端接口。
- 是否影响部署配置。
- 是否需要更新技术文档。

只有任务明确要求时才更新 `D:\lekang\docs\backend-status.md`。不得擅自修改总进度文档 `D:\lekang\docs\status.md`。
